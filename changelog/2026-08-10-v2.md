## 2026-08-10 — v2

The whole of v2 was built in one session, before this repo existed, so its iteration history isn't in git. What
follows is the reasoning behind the decisions that were argued over. Everything from here on gets real commits.

### Why five stages instead of two

The old flow had no step that read the real code before planning, and no step that captured anything afterwards.
`task-investigate` exists because plans were being written against imagined method behaviour. `task-learn` exists
because every session started from zero.

### The rule that does the most work

Every claim about existing code carries the file and line. Not because citations are nice, but because a claim
read from the code and a claim guessed from a method name look identical without one. This is the only mechanism
that makes shallow reading *visible*.

Everything else follows the same shape: turn an instruction you can't check into an output you can.

### Rules layered by scope, not by topic

`common/` for how to work anywhere, `stacks/` for one kind of project, per-repo for one repo. The test: if you can't
state it without naming a specific project, it belongs one layer down.

### Skills vs rules, and the hybrid

A rule loads every turn; a skill loads when the task matches its description. Most things people write as skills
should be rules and vice versa.

`why-this-exists` is a third case: it fires *mid-task*, the moment something is about to be deleted, and nothing in
the original request predicts that. Description-matching has nothing to match on. So the always-on rule carries the
trigger and the cheapest first check, and the skill carries the rest.

That gave a general shape worth reusing: **an always-on rule should never be only a pointer.** Give it an action
that stands alone, then point at the skill for depth. Otherwise it does nothing on the days the pointer is ignored.

### Default to keep, not delete

When the agent can't work out why code exists, it keeps it and asks. That occasionally leaves genuinely dead code
around — the right trade, because a stale line costs almost nothing and a resurrected bug costs a day and reaches
production first.

The tie-breaker against the cleanup rule: the diff decides. Code added since the plan's base commit is the agent's
own and gets deleted without ceremony. Only pre-existing code gets the benefit of the doubt. Without that split,
the cautious rule would have protected the agent's own abandoned attempts.

### Files, not conversation — but not per stage

State lives in files so a compaction or crash costs nothing. That was initially mistaken for "one chat per stage",
which is wrong: staying in one session keeps the reasoning behind decisions, which never reaches the files.

`task-review` is the one real exception, and not for context reasons. A model reviewing code it just wrote treats
its own reasoning as evidence. More context makes that worse.

### Review findings need a decision, not just a fix

Each finding gets marked fix now, backlog, or won't fix — the last one **with a reason**, recorded. Without that
bucket, every disagreement evaporates when the chat closes and the same finding returns next review, which is how
people learn to stop reading review output.

A "won't fix" with a reason is usually a `GOTCHAS.md` entry: a thing that looks wrong and isn't.
